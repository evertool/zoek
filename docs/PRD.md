# 得闲开台（zoek）— 微信小程序产品需求文档

> 版本：v1.3
> 更新日期：2026-09-10
> 状态：MVP 需求确认版

---

## 一、产品定义

### 1.1 产品定位

得闲开台是一款轻量麻雀牌局积分记录工具。不计算番种，不读取微信好友列表，不记录现金，只保存玩家根据现场规则确认后的积分。

MVP 主流程：

```text
登录 → 一键开台 → 分享二维码 → 扫码入台 → 开始计分
→ 每位玩家提交自己的本局积分 → 全员复核 → 锁定本局
→ 开始下一局 → 结束牌局 → 结算 → 历史
```

### 1.2 MVP 保留

- 微信登录
- 创建牌台，创建者自动入台
- 生成牌台微信二维码和小程序分享入口
- 2～4 人微信扫码入台
- 每位玩家只能提交自己的本局增量积分
- 提交状态、当前局号、已完成局数
- 全员提交后的复核阶段
- 零和校验
- 锁定前修改自己的提交
- 锁定后补分/退分修正
- 任意已入台玩家开始下一局
- 台主结束牌局
- 本台结算排名
- 简单趣味称号
- 私密原生分享
- 牌局历史和单场详情

### 1.3 MVP 不做

- 现金、金额、欠款、付款、转账或积分兑换
- 自动番种识别和麻雀规则引擎
- 微信好友列表、微信群成员列表
- 跨牌台好友排名和圈子排行
- 游客模式
- 座位、庄家、自摸、点和等麻雀扩展字段
- 撤销已锁定局、直接覆盖已锁定局
- 图片生成、COS、订阅消息
- 趋势图、月报、年度报告、数据导出

### 1.4 后续趣味性

#### P1：雀友榜

用户只能通过共同牌台、邀请码或分享链接主动建立雀友关系，双方确认后生效。不调用微信好友关系。

- 默认统计最近 30 天
- 至少完成 3 局才进入正式榜单
- 展示完成场次、胜场、前三率、平均名次
- 不跨不同积分规则直接比较累计积分
- 同分并列
- 用户可以隐藏自己、解除雀友关系
- 支持“再来一局”：复制参与者名单生成新牌台，所有人重新确认加入

#### P2：成就和分享

- 周榜、月榜、赛季榜
- 连胜、最大翻盘、稳定发挥等可解释成就
- 精美结算卡、公开只读摘要页、趋势图

所有趣味功能不得涉及现金、抽奖、付费竞争或强制公开积分。

### 1.5 设计原则

1. **每人自己记**：玩家只能提交自己的本局积分，不能代填他人。
2. **先复核后锁定**：全员提交后先展示完整本局数据，再锁定。
3. **原始记录可追溯**：锁定后不覆盖原始分数，错误通过调整记录修正。
4. **整台积分守恒**：每局锁定时总和必须为 0；补分和退分是等额转移。
5. **状态明确**：页面始终显示当前局号、已完成局数和提交进度。
6. **服务端为准**：权限、状态、校验、锁定、结算由服务端决定。
7. **非现金趣味**：称号和排名只表达牌局结果，不表达金钱输赢。

### 1.6 术语

| 术语 | 定义 |
|---|---|
| 台主 | 创建牌台的用户，自动入台，拥有开始、取消和结束权限 |
| 玩家 | 已登录并成功加入牌台的用户 |
| 本局积分 | 玩家本局获得或失去的增量积分，可为正、负或 0 |
| 当前局 | 正在提交或复核的局，显示局号，如“第 3 局” |
| 复核 | 全员提交后展示本局完整分数和总和的阶段 |
| 完成局 | 复核通过、总和为 0、已锁定的局 |
| 成员锁定 | 第 1 局首次提交后固定参与者，后续不能加入新人 |
| 补分 | 发现少记后，从发起方转给另一位玩家积分 |
| 退分 | 发现多记后，将多收积分转回另一位玩家 |
| 积分调整 | 经对方确认的补分或退分转移记录 |

## 二、业务规则和状态机

### 2.1 牌台状态

```text
forming   已创建，等待至少 2 人
active    计分中
ended     已结束，原始记录只读，保留 24 小时调整窗口
expired   长时间未开始自动失效
cancelled 台主主动取消
```

状态规则：

1. 创建者自动加入，牌台最多 4 人。
2. 至少 2 人才能开始计分；不要求满 4 人。
3. `forming` 状态允许扫码加入、开始或取消。
4. 首局首次提交前允许加入；第一次提交成功后锁定成员快照。
5. 成员锁定后，二维码仍可打开牌台，但不能加入新人。
6. `forming` 超过 24 小时仍未开始，自动变为 `expired`。
7. `forming` 且没有完成局时不能结算；台主只能取消或等待自动失效。
8. `active` 没有未完成局时，台主可以结束牌局。
9. `ended` 后二维码失效，原始局、成员和局号只读。
10. `ended` 后只允许 24 小时内的积分调整请求写入；窗口结束后永久只读。

### 2.2 局状态

```text
open            等待当前成员提交
review          全员提交，等待查看完整分数并确认
locked          复核完成且总和为 0
ready_for_next  本局完成，可结束或创建下一局
```

状态流转：

```text
forming
  → active + 第 1 局 open
  → 全员提交
  → review
  → 任意成员确认且总和为 0
  → locked / ready_for_next
  → 任意成员创建下一局
  → 第 2 局 open
  → ……
  → 台主结束
  → ended
```

规则：

1. 每局由服务端生成连续局号，从 1 开始。
2. 当前成员全部提交后进入 `review`，不会直接跳过复核。
3. `review` 阶段所有成员看到本局全部分数、总和和确认按钮。
4. `review` 阶段任意成员都可以修改自己的分数；修改后重新计算总和。
5. 总和为 0 时，任意已入台成员点击“确认锁定”即可锁定；点击前必须二次确认。
6. 总和不为 0 时不能锁定，显示差额并要求修改。
7. 锁定后才能创建下一局；下一局由任意已入台玩家显式创建。
8. 并发点击创建下一局只能成功创建一个局，重复请求返回已创建的局。
9. 当前局为 `open` 或 `review` 时，不能创建下一局和结束牌局。
10. 牌局结束后不再创建新局。

### 2.3 本局积分

1. 每位当前成员提交一个整数本局积分；积分是增量，不是累计值。
2. 积分可以为正数、负数或 0。
3. 每位玩家只能提交自己的分数，服务端从登录身份获取玩家 ID。
4. 未提交时显示“待提交”；提交后显示“已提交”。
5. `open` 阶段不显示其他玩家具体分数，只显示提交状态。
6. 进入 `review` 后显示所有玩家具体分数和本局总和。
7. 总和为 0 才能锁定本局；总和不为 0 保持 `review`。
8. 锁定前修改只覆盖自己的当前提交，不产生调整记录。
9. 原始提交锁定后不可覆盖、删除、撤销。
10. 流局按普通一局记录，所有玩家提交 0 分。

## 三、记错处理、提示和结算

### 3.1 锁定前记错

玩家发现自己少记或多记，直接修改自己的提交：

```text
原提交 +16
→ 修改为 +8
→ 重新进入 review
→ 服务端重新计算总和
→ 总和为 0 后确认锁定
```

### 3.2 锁定后记错

锁定后不修改原始局记录，使用积分调整。

#### 补分

```text
张三发现少给李四 8 分
→ 张三发起“补分 8 分”
→ 选择李四
→ 李四确认
→ 张三 -8，李四 +8
```

#### 退分

```text
张三发现多收李四 8 分
→ 张三发起“退分 8 分”
→ 选择李四
→ 李四确认
→ 张三 -8，李四 +8
```

数据层统一表示为：

```text
from_player - amount
 to_player + amount
```

调整规则：

1. 只有参与者可以发起调整。
2. 接收方必须是同一牌台的另一位玩家。
3. 调整数值必须为正整数。
4. 调整必须关联具体牌局和局号。
5. 接收方确认后才生效；拒绝、取消、过期不改变原始积分。
6. 待确认调整不计入累计积分和结算；已确认调整计入结算。
7. 调整记录保存发起人、接收人、类型、数值、原因、处理人、处理时间和状态。
8. 调整不会覆盖原始局分数，只在详情页作为追加记录展示。
9. 调整始终保持整台总积分不变。
10. 牌局结束后 24 小时内允许发起和确认调整；窗口结束后永久只读。
11. 结束后的调整确认会更新最新结算，并显示“结算已更新”和更新时间。

调整状态：

```text
pending   待接收方确认
accepted  已确认并生效
rejected  已拒绝
cancelled 已取消
expired   已过期
```

### 3.3 提示文案

#### 普通计分

| 场景 | 提示 |
|---|---|
| 提交正分 | `已提交本局 +16 分，等待其他玩家提交` |
| 提交负分 | `已提交本局 -16 分（本局扣除 16 分）` |
| 提交 0 分 | `已提交本局 0 分` |
| 修改成功 | `已更新本局积分：+16 → +8` |
| 等待提交 | `已提交 2/3 人，还差 1 人` |
| 进入复核 | `第 3 局已提交完成，请核对本局分数` |
| 复核通过 | `第 3 局已完成，本局总和为 0` |
| 零和失败 | `本局总和为 +8，请检查并修改自己的积分` |
| 开始下一局 | `第 4 局开始，请提交本局积分` |
| 结束失败 | `还有第 4 局未完成，完成后才能结束牌局` |

#### 积分调整

| 场景 | 提示 |
|---|---|
| 发起补分 | `补分请求已发送，等待李四确认` |
| 发起退分 | `退分请求已发送，等待李四确认` |
| 收到补分 | `张三申请补给你 8 分` |
| 收到退分 | `张三申请退回 8 分` |
| 确认成功 | `积分调整已生效：张三 -8 分，你 +8 分` |
| 拒绝成功 | `积分调整未生效，原积分不变` |
| 结束后更新 | `积分调整已生效，结算已更新` |
| 调整过期 | `积分调整已过期，原积分不变` |

### 3.4 当前局号和完成局数

当前局号是 P0 信息，不能由前端自行推算。服务端必须返回：

- `current_round_number`：当前局号；牌局结束后为 `null`
- `completed_rounds`：已锁定完成局数
- `submitted_count`：当前局已提交人数
- `member_count`：当前成员数

必须显示的位置：

- 首页：`第 3 局 · 已完成 2 局`
- 房间页：`当前第 3 局`
- 计分页顶部：`今晚麻雀 · 第 3 局`
- 复核提示：`第 3 局已提交完成`
- 完成提示：`第 3 局已完成`
- 结算页：`共 8 局`
- 历史详情：每条记录显示局号

### 3.5 本台结算和趣味称号

结算展示：

- 共完成 N 局
- 每位玩家最终积分
- 排名和并列名次
- 胜场/完成局数
- 已确认调整数量
- 最新结算更新时间（有结束后调整时显示）

称号只基于本台数据：

- 本台冠军：最终积分最高
- 单局最高：单局获得积分最高
- 最大翻盘：累计积分从负转正幅度最大
- 稳定发挥：局间积分波动较小

称号计算规则必须可解释；数据不足时不显示称号，不随机生成。

## 四、页面和流程

### 4.1 页面结构

```text
pages/
├── index/       首页：进行中牌局和历史入口
├── create/      开台（一键创建，无表单，首页点击直接跳转台间页）
├── room/        房间、二维码和成员列表
├── score/       当前局提交和复核
├── adjustment/  补分/退分
├── settlement/  结算
├── history/     历史列表
├── detail/      单场详情
└── profile/     登录状态和昵称
```

底部导航：

```text
牌局 | 历史 | 我的
```

### 4.2 完整正常流程

#### A. 开台和入台

1. 台主登录。
2. 台主在首页点击"开台"按钮，**无需填写任何信息**，服务端自动创建牌台。
3. 服务端创建 `forming` 牌台，台主自动加入；台名默认为"得闲开台"+日期时间，如"得闲开台 9月8日"。
4. 服务端生成不可猜测的邀请 token，页面展示微信二维码（普通二维码，非小程序码）。
5. 其他用户用微信扫码，登录后进入牌台预览。
6. 用户确认昵称和加入，服务端检查人数、状态、token 和重复加入。
7. 至少 2 人时台主点击"开始计分"。
8. 服务端创建第 1 局，返回 `第 1 局 · 已完成 0 局`。

> **设计原则**：开台操作零摩擦，一键即开。台名自动生成，无需用户输入。

#### B. 一局计分

1. 当前成员各自输入自己的本局积分。
2. 每人提交自己的分数，服务端保存当前提交。
3. 页面显示 `已提交 n/m 人` 和待提交成员。
4. 全员提交后进入 `review`。
5. 所有人看到本局全部分数、总和和确认按钮。
6. 发现错误时，各自修改自己的分数。
7. 总和为 0 时，任意成员二次确认锁定。
8. 服务端事务锁定本局，更新完成局数和累计积分。
9. 任意成员点击“开始下一局”，服务端幂等创建下一局。

#### C. 牌局结束

1. 台主点击“结束牌局”。
2. 服务端检查当前没有 `open/review` 局，且至少完成 1 局。
3. 服务端事务写入结束时间和结算快照，牌台变为 `ended`。
4. 结算页展示积分、排名、局数和称号。
5. 牌局自动进入所有参与者的历史列表。

#### D. 锁定后修正

1. 参与者打开具体局详情，点击“补分/退分”。
2. 选择对方、填写正整数和原因，发送请求。
3. 对方在牌台页看到待确认请求。
4. 对方同意或拒绝。
5. 同意时服务端事务写入确认结果并重新聚合结算。
6. 双方和历史详情显示调整记录及最新积分。
7. 24 小时窗口结束后，调整入口关闭。

## 五、异常和恢复闭环

### 5.1 统一错误处理

每个业务错误返回稳定的 `code`、用户可读 `message` 和 `action`：

```json
{
  "code": "ROUND_NOT_READY",
  "message": "还有 1 位玩家未提交",
  "action": "REFRESH_GAME"
}
```

前端根据 `action` 执行：

```text
RELOGIN        重新登录
REFRESH_GAME   重新拉取牌台
RETRY          重试原请求
BACK_TO_ROOM   返回房间
READ_ONLY      切换只读
```

### 5.2 场景矩阵

| 场景 | 服务端处理 | 页面动作 |
|---|---|---|
| 微信登录失败 | 不创建会话 | 提示重试 |
| token 过期 | 返回 `AUTH_EXPIRED` | 重新登录后回到原页面 |
| 二维码 token 不存在/过期 | 拒绝加入 | 显示邀请失效 |
| 牌台满员 | 拒绝新成员 | 显示牌台已满 |
| 成员已锁定 | 拒绝新成员 | 显示已开始，返回牌台 |
| 重复扫码 | 返回已有成员 | 直接进入牌台 |
| 并发抢最后席位 | 数据库唯一约束/事务裁决 | 一方成功，另一方提示已满 |
| 创建重复点击 | `request_id` 幂等 | 返回原牌台 |
| 首次提交超时 | 服务端按 request_id 返回原结果 | 重新拉取状态，不重复提交 |
| 旧页面提交旧局 | 校验 round ID 和状态 | 拉取当前局 |
| 其他人已锁定本局 | 拒绝修改 | 显示本局已完成 |
| 零和不为 0 | 保持 `review` | 显示总和和修改入口 |
| 两人同时确认锁定 | 行级锁/事务 | 一个成功，另一个返回已锁定 |
| 创建下一局重复点击 | `request_id` + 唯一局号 | 返回同一下一局 |
| 当前局未完成却结束 | 拒绝结束 | 显示待提交/待复核状态 |
| 空牌局结束 | 拒绝结算 | 只能取消牌台 |
| 结束重复点击 | 幂等返回结算 | 进入结算页 |
| 结束与最后锁局并发 | 事务锁定牌台和当前局 | 以先完成的合法状态为准 |
| 补分重复确认 | 状态条件更新 | 返回已处理结果 |
| 补分过期后确认 | 拒绝确认 | 显示调整已过期 |
| 调整接收方拒绝 | 不改变积分 | 原始结算不变 |
| 历史加载失败 | 不修改本地旧数据 | 提示重试 |
| 牌局已结束写原始记录 | 拒绝 | 切换只读并刷新 |

### 5.3 数据一致性要求

- 所有写操作后端校验用户、牌台、成员、局状态和权限。
- 所有创建、提交、确认、结束请求支持 `request_id` 幂等。
- 最后一人提交、复核锁定、创建下一局和结束牌局使用事务。
- 结算不接受客户端累计分，始终由服务端聚合。
- 失败请求不得部分写入；事务失败全部回滚。
- 页面回到前台或重新进入时从服务端刷新，不以本地缓存作为最终状态。

### 7.1 MVP 架构

```text

        ↓ HTTPS

        ↓

```

#### 后端工程化基础设施

开发阶段即建立以下工程化设施，不等到上线才补：

| 设施 | 实现 | 说明 |
|---|---|---|
| 配置管理 | `internal/config/config.go` | YAML 文件 + 环境变量覆盖；`config.example.yaml` 为模板 |
| 结构化日志 | `internal/logger/logger.go` | 基于 zap；支持 JSON/console 格式、多级别、文件输出 |
| 请求日志 | `middleware.Logging()` | 每个请求记录 method、path、status、latency、request_id、client_ip |
| 请求 ID | `middleware.RequestID()` | UUID 自动生成，贯穿请求全链路 |
| CORS | `middleware.CORS()` | 可配置白名单域名 |
| Panic 恢复 | `middleware.ErrorHandler()` | 捕获 panic，记录结构化日志，返回统一 JSON 错误 |
| 优雅关闭 | `main.go` | 监听 SIGINT/SIGTERM，等待处理中请求完成再退出 |
| 数据库日志 | GORM Logger 适配 | 慢查询告警（>200ms），SQL 日志桥接到 zap |
| 事务封装 | `store.Transaction()` | 关键写操作（锁局、结束牌局、确认调整）使用事务 |
| JWT 过期 | `JWTManager.TokenExpiry` | 可配置 Token 有效期，默认 7 天 |

### 7.3 数据约束

- `round_submissions.score` 和 `score_adjustments.amount` 使用 `INT`；Go 使用 `int64` 计算并校验范围。
- `score_adjustments.amount` 必须大于 0；双方必须属于同一牌台且不能相同。
- `round_submissions` 保证一局一人一条当前提交。
- 原始提交锁定后永不删除或覆盖。
- `games.invite_token_hash` 只保存 token 哈希，微信二维码不暴露可猜测的牌台 ID。
- `join_expires_at` 默认创建后 24 小时；成员锁定或结束后立即失效。
- 调整 `expires_at` 默认创建后 24 小时；过期请求不能确认。
- 结算最终积分由 locked 局原始提交加 accepted 调整聚合，不保存客户端可写的最终分字段。

最终积分：

```text
玩家最终积分
= locked 局 round_submissions.score 之和
- 作为 from_player 的 accepted amount 之和
+ 作为 to_player 的 accepted amount 之和
```

| 项目 | 目标 |
|---|---|

## 十、开发顺序和自动验证

### 10.1 开发顺序

1. 产品契约和状态机测试
2. Go 项目、数据库迁移和 scoring 纯函数
3. 登录、开台、邀请、微信扫码入台
4. 提交、review、锁局、下一局
5. 结束、结算和历史
6. 补分/退分及结束后 24 小时窗口
7. 小程序页面和真机流程
8. 本台称号和私密原生分享
9. P1 雀友关系和雀友榜

### 10.2 固定验证入口

代码创建后建立一个统一入口：

```text
make verify
# 或 scripts/verify.sh
```

验证顺序：

```text
Markdown/格式
→ Go format/vet/lint/编译
→ scoring/状态机/结算单测
→ 数据库迁移和临时数据库测试
→ API 契约/权限/幂等/并发测试
→ 小程序构建和页面逻辑测试
→ 多设备微信扫码、弱网、刷新恢复 E2E
→ 安全、隐私和包体积检查
```

### 10.3 自动修复边界

- 自动修复只处理可复现且明确属于代码缺陷的问题。
- 修复前保存失败日志、最小复现和失败测试。
- 每轮修复必须新增或完善回归测试。
- 最多自动尝试 2～3 轮。
- 禁止删除测试、放宽断言、跳过 lint、吞掉错误或修改验收标准。
- 需求矛盾、权限/隐私、结算结果、数据库迁移和安全问题必须停止自动修复，转人工确认。
- 修复后必须重新执行全量验证。

### 10.4 重构边界

- 全量验证通过后才能重构。
- 一次只做一个结构性变化。
- API 和数据库契约不变，除非有单独迁移计划。
- 重构后重新执行全量验证。
- 重构失败优先回滚重构，不把业务修复和重构混在同一轮。

### 10.5 是否制作 Skill

当前仓库只有 PRD，没有业务代码。**现在不制作自动执行代码的 Skill。**

先用代码、测试、迁移和 `make verify` 固化业务规则。核心规则必须存在于领域代码和测试中，不能藏在 Skill 提示词里。

等一个完整纵向切片通过验证后，再制作受控的 `zoek-implementation` Skill。Skill 只负责：

1. 读取已批准任务和验收标准。
2. 定位目标模块。
3. 按既定目录实现。
4. 执行固定验证命令。
5. 输出变更、测试结果和剩余风险。

Skill 不得：

- 自行修改 PRD或扩大范围
- 跳过失败测试
- 自动执行破坏性数据库操作
- 自动发布生产
- 在需求不明确时猜测规则
- 用重构掩盖业务错误

## 八、v1.3 新增功能说明（2026-09-10）

### 8.1 排位模式（4 人局散台即排位）

- **参与资格**：只有 4 人局散台（active → ended）才结算排位；2/3 人局与取消局不参与。
- **星级规则**：净赢家（总分第 1，并列同名次）+1 星；末位 -1 星；第二、第三名为平不扣星；全场同分（如连续流局）按平处理。
- **连胜奖励**：胜场后连胜达 3~5 场，该场额外 +1 星；达 6 场及以上额外 +2 星（共 3 颗）。平/输清空连胜。
- **保底保护**：星级下限 0，九品 0 星输局不掉星。
- **六品雀位**：九品·初入雀境(3星) → 八品·市井雀手(3星) → 六品·茶铺雀侠(4星) → 四品·省城雀师(4星) → 二品·岭南雀宗(6星) → 至尊·无双雀神(无上限)。星满自动升段，段内小段 I~V 由段内星数推导。引擎见 `backend/internal/rank`。
- **数据表**：`users` 新增 `rank_stars/rank_wins/rank_draws/rank_losses/rank_streak/rank_best_streak/rank_points`；`rank_settlements` 记录每场变动（`(game_id,user_id)` 唯一，保证幂等）。迁移文件 `005_add_rank_mode.sql`。
- **接口**：`GET /api/v1/rank/me`（段位+赛季数据）；`GET /api/v1/games/:id/history` 返回 `rank_changes`；雀友榜与个人资料响应携带段位。
- **入口**：排位页 `pages/rank/rank`（段位卡/升星机制/六品徽标）；个人中心昵称旁段位胶囊；雀友榜行内段位徽标；结算页「本场 ±N 星」卡。

### 8.2 记录页（开台手账）

- 日期筛选：近 7 天 / 近 30 天 / 全部（`days` 参数）。
- 标签筛选：胜 / 平 / 负（按本场名次，第 1 名=胜、末名=负、中间=平；单人取消局恒为平）。
- 分页：`page/page_size`，`has_more` 触底加载。
- 列表项：我的净得分、名次、局数、时长、对局雀友、排位标记、改分记录提示。

### 8.3 对局详情三页（数据源 `GET /games/:id/history`）

- **每局详情页** `pages/game-detail`：我的净得分、全场收支总览（风位+名次徽标）、逐局分值流向流水（新→旧，含已确认改分「修正」行，右侧为我的净流向）。
- **手帐明细页** `pages/game-ledger`：四风位总览、雀王功名录（本台冠军/单局食大茶饭=单局最高得分/稳如泰山=最长连续不败）、逐局各家分值、合影留念（本地选图预览）、原班雀友再开一局（创建新台）。
- **图表分析页** `pages/game-chart`：累计积分走势（Canvas 逐局四色折线 + 线性递画动画 + 图例点击筛选）、战局复盘（单局最大爆发/全场控盘王/局间振幅极差）、逐局单局净胜负柱状图。校对差额 = |Σ 玩家总分|。

### 8.4 牌台互斥

- 一个用户同时只能有一张进行中（forming/active）的牌台：开台或加入其他台时返回 `409 ALREADY_IN_GAME` 并附 `game_id`，前端引导「去看看/去我的牌台」。
- 散台、取消、过期后自动释放。

### 8.5 牌局页（首页）

- 当前牌局至多一张卡；头像/昵称/风位 5 秒轮询实时刷新（不展示他人得分，遵守开牌阶段隐私）。
- 「邀请雀友」分享按钮仅在未满 4 人且未记分时显示；满人或已记分自动隐藏；「录入计分」入口移除（进房间记分）。
- 最近战绩：真实最近 3 场（我的得分/名次），「全部记录」跳转记录 Tab，条目可进每局详情页。

### 8.6 雀友榜

- 时间筛选 `days=7|30|0`（默认 30）真实生效；**同台切磋 ≥ 3 场方可入榜**；最多展示前 20 人。
- **积分榜与段位榜同口径：只统计满 4 人的排位局**（2/3 人局不参与两个榜单的排名与统计）。
- 积分榜按**窗口内净胜分**降序排名（同分依次比胜率、场次）；段位榜按排位累计星级降序。
- 双榜切换：积分榜（按胜率/平均名次）/ 排位榜（按排位累计星级）。
- 行内新增：连赢最高（窗口内连续第 1 名场数）、单场最高分、规则标签：
  - 🔥 连胜王：窗口内最高连胜 ≥ 3；
  - 🍀 今晚手气王：今日单场最高分 ≥ 20；
  - 🛡 稳如泰山：≥5 场且场均 |得分| ≤ 10；
  - 🔄 大翻盘赢家：单场从最深落后翻回（终局 − 最低点 ≥ 30 且终局为正）；
  - 🪑 常客：≥10 场；🚶 铁脚：≥50 场；👑 雀神：≥30 场且胜率 ≥ 60%。
- 「约开台」：点击自动确保有一张自己的台（没有则自动开台），随后拉起微信分享发送邀请链接（`onShareAppMessage` 返回入台路径）。
- 列表不再显示「你本人」文字标记（保留高亮卡样式）。

### 8.7 换位

- 长按空位：立即换座（`POST /games/:id/swap_seat`），无需对方同意。
- 长按他人座位：换位申请弹窗（确认流程开发中）。
- `game_players.seat` 座位号 1-4，加入时分配最小空座，玩家列表按座位排序；迁移 `004_add_game_player_seat.sql`。
